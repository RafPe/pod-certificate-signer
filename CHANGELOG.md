## [3.1.0] - 2026-11-11

- A new `--allow-pod-annotations` flag (Helm `signer.allow_pod_annotations`) gates the deprecated fallback that reads certificate configuration from the pod's own annotations. It defaults to on until the fallback is removed in 4.0.0; operators who have moved every workload to `spec.unverifiedUserAnnotations` can set it to false now, so pod annotations stop being a second requester-controlled input.
- A `CERTIFICATE` block in the signer's existing ClusterTrustBundle that does not parse now fails startup closed, like a read error does, instead of being skipped with a log line. The bundle is the controller's only record of its previous-CA history, so a silently shortened history would have been written back on the next publish. A corrupt bundle is not retried either: it reads back the same every time, so startup fails on the first read instead of spending the retry budget.
- Errors from loading the CA key pair, at startup or on a reload, now name the certificate and key files they came from.
- Controller log lines are reworded as lowercase fragments (for example `request is already terminal; nothing to do`, `published ClusterTrustBundle`), a transient reconcile error is logged once by controller-runtime instead of twice, a denial is logged at info rather than error level, and an absent ClusterTrustBundle at startup is logged at error level instead of as an info line prefixed `WARNING:`. Log-based alerts or searches that match the old wording need updating.
- The denial for an IP address requested in the CSR under `--honor-csr-sans`, without `--allow-unverified-identities`, now starts with `CSR IP addresses:`, matching the `CSR DNS names:` prefix on the DNS path.
- A request denied because it has neither a common name nor a SAN - a pod name too long for both - now says in the denial message why the default DNS SANs were dropped, instead of in a separate warning event emitted before the denial.
- The `duration` and `refresh` annotations now resolve `${...}` placeholders exactly like every other configuration annotation, so a value using interpolation is either expanded or, with `--enable-annotation-interpolation=false`, denied, rather than failing to parse as a duration.
- A configuration item present with an empty value - in `spec.unverifiedUserAnnotations` or, on the deprecated fallback, in the pod's own annotations - now denies the request instead of being treated as absent, which silently routed it onto the pod-annotation fallback or the default.
- CA reload, signing and watcher errors drop their "failed to"/"unable to" prefixes and carry the component name once (`load key pair: ...`, `parse certificate: ...`, `ca-watcher: watch directory ...`), matching the rest of the codebase; anything matching controller logs on the old wording should match on the remainder.
- Every value the signer still reads from the deprecated pod-annotation configuration path is now logged, so remaining users can be found before the fallback is removed in 4.0.0. Unknown keys in pod annotations are still ignored rather than denied: pod annotations are shared with other consumers, and a signer-name prefix cannot tell a typo from the key of another signer whose name extends this one.
- The readiness check that tracks the CA watcher and reload health is now named `certificate-authority` instead of `readyz`, so `/readyz?verbose` says which component is not ready. Anything that probes `/readyz/readyz` directly must switch to `/readyz/certificate-authority`; the `/readyz` endpoint itself is unchanged.
- The denial for an unrecognized signer annotation key now reads `unrecognized key "<key>" in spec.unverifiedUserAnnotations`, naming where the key was found, instead of `unrecognized user annotation key "<key>"`. Alerts or searches matching the old wording need updating.
- A Denied or Failed event now carries its message verbatim. The message was used as a format string, so a `%` in a rejected annotation value came out garbled in `kubectl describe` (for example `%!d(MISSING)`).
- The `--max-concurrent-reconciles`, `--max-previous-ca-certs`, `--reconcile-timeout`, `--signer-name` and `--cluster-fqdn` help texts are capitalized and punctuated consistently with the other flags, and `--signer-name` now says it matches PodCertificateRequests rather than CSRs.
- The `--leader-election-id` help text names the Lease that coordinates leader election; it used to say ConfigMap, which the controller has not used since leader election moved to Leases.
- A metrics scrape or CA reload no longer waits for an in-flight certificate signing to finish: signing now runs outside the CA lock.
- A ClusterTrustBundle publish or CA reload that is abandoned because the controller is shutting down is no longer recorded as a failed publish or reload: it no longer increments the failed counters or flips readiness on the way out.

## [3.0.1] - 2026-10-21

- A leader shutting down now releases its leader-election Lease instead of leaving a standby to wait out the 15 second lease duration, so a rolling upgrade hands leadership over - and resumes signing, which is leader-gated - in about a second rather than about sixteen.
- Update controller-runtime to 0.25.1, Ginkgo to 2.33.0, Gomega to 1.43.1, the Go container builds to 1.27.1, and the docker and codeql GitHub Actions.
- Update Kubernetes libraries to 0.37.1, controller-runtime to 0.25.2, Gomega to 1.44.0, OpenTelemetry to 1.45.0 (fixes GO-2026-6505), golang.org/x/net to 0.60.0 (fixes GO-2026-6610 through GO-2026-6617), and the codeql and release-drafter GitHub Actions.
- Update controller-runtime, Prometheus client, Ginkgo, Gomega, Go container builds to 1.27.0, and the distroless runtime image.
- Update google.golang.org/grpc to 1.83.1, which fixes GO-2026-6348.
- `make dev-ca` generates the development CA with Go instead of openssl, so it works on macOS where LibreSSL silently produced an invalid key.
- `Sign` and `CertificateNotAfter` no longer dereference the CA certificate without a nil guard. An authority that somehow holds no certificate - possible only through a construction path that defers the first load, since `New` fails closed - now refuses to sign with the same "CA unusable, requeue" classification as an expired signer, and reports its expiry as a zero timestamp instead of panicking. The second guard matters beyond signing: `CertificateNotAfter` runs on every metrics scrape, where a panic takes down the scrape rather than being recovered.
- The signer now refuses a CA certificate whose `NotBefore` lies more than five minutes ahead of its clock, instead of loading it and signing certificates no peer can verify. A not-yet-valid CA - typically one minted by an external PKI whose clock runs ahead of the node's - previously passed validation, so the signer reported healthy while every leaf it issued failed chain verification on the peer side. Such material is now rejected at load like any other unusable CA: the last-good CA stays in place and keeps signing, the reload failure is logged as `CA certificate is not yet valid`, and the certificate is also kept out of the published ClusterTrustBundle, where the same check gates the previous-CA history. The five-minute tolerance is what keeps benign clock skew around a fresh rotation from turning into a reload failure.
- Build the signer with Go 1.27.3, which fixes CVE-2026-111943 in crypto/x509 (golang/go#82345).

## [3.0.0] - 2026-08-27

- The signer now speaks the GA `certificates.k8s.io/v1` API and requires Kubernetes 1.37 or newer; the chart's `kubeVersion` moves to `>= 1.37.0-0` and installs on older clusters are refused. Nothing needs enabling on the cluster any more: `PodCertificateRequest` and `ClusterTrustBundle` are served by default in 1.37, so the `PodCertificateRequest`, `ClusterTrustBundle` and `ClusterTrustBundleProjection` feature gates and the `certificates.k8s.io/v1beta1` runtime-config entry can all come out of your apiserver configuration. The GA type drops `spec.pkixPublicKey`, so the signer no longer honours it and reads the subject public key only from the PKCS#10 stub every 1.37 kubelet sends - a request that somehow carries neither is denied with `UnsupportedKeyType` rather than signed. The `-0` suffix on the version constraint is deliberate: it admits managed distributions whose version strings carry a suffix, such as `1.37.2-eks-abc123`, which semver reads as prereleases and a bare `>= 1.37.0` would reject.

## [2.4.0] - 2026-08-21

- Two outages that were previously visible only in logs are now alertable. `podcertificatesigner_ca_expiration_timestamp_seconds` says when the signer will stop being able to issue - past that point requests requeue silently and pods sit in ContainerCreating - and `podcertificatesigner_ca_reload_last_success_timestamp_seconds` catches a reload loop that stopped, which no failure-based signal can, since a dropped watch or a wedged ticker produces no failures at all. Alongside them: `podcertificatesigner_ca_reload_attempts_total{result}` marks rotations and reload failures, `podcertificatesigner_ca_reload_consecutive_failures` crosses its threshold roughly five minutes before readiness flips, and `podcertificatesigner_trust_bundle_certificates` reports how many anchors the signer would publish. The four gauges are computed at scrape time from the loaded CA, so they cannot go stale relative to the reload loop. docs/operations.md carries the alert expressions.
- A PodCertificateRequest the CA cannot sign yet - an expired signer, or a requested lifetime longer than the CA's remaining validity - now carries a rate-limited `CASignerUnusable` warning event, so `kubectl describe podcertificaterequest` shows why a pod is stuck in ContainerCreating instead of nothing at all. The request is still requeued rather than failed, and still records no condition, so a CA rotation can satisfy it.
- A Grafana dashboard over the signer's metric surface ships at `docs/dashboards/pod-certificate-signer.json`. Panels read through a `datasource` dashboard variable rather than a hardcoded datasource uid, so it resolves to the default Prometheus on import with nothing to edit. The operations guide says which panels sit at zero on a healthy cluster and why, so a zero is not read as a broken panel. The metrics-authentication walkthrough now also carries a plain Prometheus `scrape_config` alongside the `ServiceMonitor`, and spells out that the metrics-reader ClusterRole is named from the chart's fullname helper - a release called `pcs` renders `pcs-pod-certificate-signer-metrics-reader`, and binding a name that does not exist returns 403 on every scrape with nothing in the controller log to explain it.
- Issuance is now measurable. `podcertificatesigner_podcertificaterequests_total{outcome,reason}` counts terminal outcomes and carries the signer's SLI - a denial returns success from the reconciler, so controller-runtime's own counters record it as one. `podcertificatesigner_podcertificaterequest_requeues_total{reason}` counts retries separately, so `{reason="CASignerUnusable"}` rising with nothing terminal alongside it names the case where requests hang and pods sit in ContainerCreating. `podcertificatesigner_podcertificaterequest_drops_total` counts requests dropped because their pod is gone, which previously left only an Event behind. No label carries a pod, namespace or request identity, so the number of series does not grow with the cluster.
- The `ctb_publish_failures_total` metric is renamed to `podcertificatesigner_clustertrustbundle_publish_attempts_total`, and counts every publish attempt by result rather than only the failures - replace an alert on the old name with `increase(podcertificatesigner_clustertrustbundle_publish_attempts_total{result="failed"}[15m]) > 0`. Counting successes too makes a zero failure count interpretable: `{result="unchanged"}` standing still is a leader that stopped publishing, and `{result="updated"}` without a CA rotation to explain it is somebody editing the cluster trust anchors out from under the signer. All custom metrics now carry the `podcertificatesigner_` prefix, and the surface they belong to is bounded by ADR-0005.
- The operations guide now carries a CA rotation runbook: budget up to ~6 minutes for a new CA to reach running workloads (kubelet's 5-minute ClusterTrustBundle normalization cache plus one pod sync period, which no flag shortens), rotate with an overlap window rather than as a swap, re-read `ca.crt` in the application because kubelet rewrites it without signalling anything, and treat a stuck `podCertificate` refresh as frozen trust anchors rather than assuming they are current.
- Previous-CA history read back from the ClusterTrustBundle at startup is now validated and trimmed to `--max-previous-ca-certs` instead of adopted verbatim, so an edited bundle is repaired by the next publish rather than becoming permanent history, and the published window never exceeds the configured bound. History is also kept by certificate identity and recency rather than insertion order, so rotating back into a CA the window already holds no longer evicts one whose certificates are still in use. A missing bundle is now reported as absence rather than as an empty history: startup still continues (a first install has no bundle) but says so loudly, and the new `--require-ca-history` / `signer.require_ca_history` makes it fail closed once the signer has published its bundle.
- Issued certificates now assert the basicConstraints extension with cA:FALSE, instead of omitting the extension and leaving each verifier to infer end-entity status from its absence. This grants no new capability and removes none - a conforming verifier already refused to treat these leaves as CAs (RFC 5280 6.1.4) - but the signer cannot enumerate the TLS stacks that verify its output, and lenient path validation around a missing basicConstraints has a long history of implementation bugs. No pathLenConstraint is set. See ADR-0003.

## [2.3.0] - 2026-08-19

- `${...}` annotation interpolation is now enabled by default (`--enable-annotation-interpolation=true`, Helm `signer.enable_annotation_interpolation: true`), so per-pod SPIFFE-style identity works out of the box. This is a usability change, not a security relaxation: placeholders resolve only from apiserver-verified request fields, and every resolved value is still checked against the pod's verified identity by exact string equality, so no identity becomes issuable that was not issuable before. Nothing that worked stops working; set the value to `false` to restore the previous behaviour of denying values that contain `${...}`. See docs/adr/0002-annotation-interpolation-on-by-default.md.
- Documented what bounds `${...}` annotation interpolation: placeholders resolve only from apiserver-verified request fields plus the operator-set cluster FQDN, and every resolved value is checked against the pod's verified identity by exact string equality exactly as a literal value is - so interpolation grants no identity a pod does not already own. The security gate is `--allow-unverified-identities`, not `--enable-annotation-interpolation`.
- SECURITY.md now describes the shipped posture rather than a superseded one - annotation-driven identity forgery is closed by default, CSR-requested SANs pass through the same identity allowlist, and the metrics endpoint is authenticated by default. The supported-versions table and the production-posture section of docs/configuration.md were corrected too.
- A CA reload that succeeds after a failure is logged again. Correcting a mismatched certificate/key pair restores the same certificate, so the change-detection added for periodic reconciliation reported "unchanged" and the confirmation was dropped to V(1) - invisible at the default verbosity to an operator who had just fixed the CA.
- The signer now reloads its CA on a 60s timer as well as on filesystem events, so a reload that failed after its retries - or a rotation whose events were dropped or never delivered - converges without a pod restart. The CA is fingerprinted, so consumers are notified and the ClusterTrustBundle republished only when the material actually changed, rather than on every event of a rotation burst. The watch also reconciles once at startup, closing the window between the initial load and the watch being registered, and no longer ignores file removals.
- The example workload manifest (`examples/workload-pod.yaml`) now issues under the identity constraints as they ship. It requested `<sa>.<ns>.svc` and a literal IP SAN, neither of which the signer grants, so copying it verbatim produced a denial unless `--allow-unverified-identities` was set. It now requests the service-account short DNS form and the service-account SPIFFE ID, uses `${cluster.fqdn}` instead of a hardcoded `cluster.local`, and carries the IP SAN as a commented escape-hatch block.
