When the signing CA changes, the leader publishes the new CA and the retained CAs in its `ClusterTrustBundle`. Kubelet updates the projected file on a pod sync. Applications must reread the file to use the new anchors.

## When does the pod see the new CA?

A pod can mount a bundle by its object `name` even when the bundle has a `spec.signerName`. On Kubernetes 1.37.0, a change to that bundle left the name-keyed cache entry in place until it expired.

The kubelet fix evicts that entry when the bundle changes. The next pod sync can then project the new anchors. [Kubernetes PR #141459](https://github.com/kubernetes/kubernetes/pull/141459)

### How we measured

On November 20, 2026, we ran one update on each of two single-node Kind clusters. Both used the default kubelet sync settings. One running pod mounted the same bundle twice, once by object name and once by signer name.

1. Verify that both mounted files contain the original CA.
2. Replace the CA in the bundle and start the clock when `kubectl apply` returns.
3. Read both files, check their SHA-256 hashes, and wait one second between checks. Record the first time each file contains the replacement CA.

These are individual observations. The pod sync schedule and polling interval affect the result. The clock excludes Secret propagation, signer reload, and bundle publication.

### Planning a rotation

Keep the old CA in the trust bundle while workloads still use certificates it signed. Wait at least one full certificate lifetime between rotations. The signer retains two previous CAs by default.
